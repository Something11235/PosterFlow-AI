# 邀请奖励

已注册用户可在侧栏或账户中心打开「邀请奖励」，复制个人邀请码或邀请链接。链接以 `?invite=PF…` 携带公开邀请码，访客进入后会打开注册窗口并自动填入。邀请码可以重复用于邀请不同的新用户。

## 发放规则

- 仅新用户注册时可以绑定一位直接邀请人，注册后不可补填或换绑。已有账号不回填邀请关系。
- 受邀用户每次成功兑换积分，邀请人额外获得兑换额度的 **10%**，受邀用户的到账积分保持不变。例如兑换 70 积分，受邀用户收到 70，邀请人收到 7。
- 当前所有积分兑换码均参与。注册赠送、管理员调整、退款和邀请奖励本身不会继续产生邀请奖励；没有多层奖励。
- 奖励以站内积分发放，直接进入邀请人的积分余额，无需手动领取。页面显示邀请注册人数、累计奖励积分和分页到账记录。
- 邀请人冻结后仍保留归属和奖励入账，账户使用受既有冻结规则约束；邀请人账号已删除、无法入账时，不影响受邀用户正常兑换。
- 上线前的兑换不补发奖励。已兑换的码重复提交，只返回原兑换结果，不会再次发放奖励。

## 数据与接口

邀请代码、注册归属、邮箱哈希占位和奖励事实保存在 `private` schema，客户端不直接读写。邮箱哈希用于防止删除账号后以同一邮箱重新绑定；不保存用于该机制的明文邮箱。用户可以编辑的注册 metadata 只作为初次注册输入，之后不会用它决定奖励归属。

`GET /api/referrals?limit=20&offset=0` 只返回已鉴权用户本人的邀请码、汇总和奖励记录。受邀人仅显示昵称，不返回邮箱、兑换码或兑换码哈希。`GET /api/referrals/validate?code=…` 是带频率限制的公开格式/有效性校验，不披露邀请人的身份。注册时数据库仍会重新验证邀请码。

`private.redeem_credit_code` 在同一事务中完成兑换、邀请人入账、积分流水和奖励事实写入。双方账户按固定顺序加锁，奖励事实和 `referral_bonus` 流水使用兑换码编号作幂等依据。任何一步失败都会回滚本次兑换；网络中断后用原兑换码重试不会重复到账。

奖励增加 `credit_accounts.balance` 和 `total_granted`，不算作购买收入，不增加 `total_spent`。积分流水类型 `referral_bonus` 在账户页显示为「邀请奖励积分」。积分精度沿用四位小数。

## 管理员统计与记录

管理员控制台的「邀请奖励」区块展示累计邀请人数、受邀用户数、相关兑换次数、兑换积分和已发奖励积分。统计覆盖全部已记录历史，不受创作统计的日期筛选影响；搜索只筛选下方明细。

- 「邀请关系」显示邀请人、受邀用户、绑定时间，以及这段关系累计兑换和奖励的积分。尚未兑换的受邀用户也会显示。
- 「兑换与奖励记录」逐笔显示双方身份、兑换额度、实际发放奖励和北京时间。奖励为零的未发放记录与已发放记录分别标识。
- 可以搜索双方昵称、邮箱或用户编号，分页查看。用户注销后仍保留关系与金额记录，缺失的昵称或邮箱以已注销及原用户编号区分。

`GET /api/referrals/admin` 和对应数据库 RPC 都检查管理员身份；普通用户无权读取。管理员接口可以查看参与双方的邮箱和编号，但不返回完整兑换码、兑换码哈希或批次导出内容。

新增的 `private.referral_redemptions` 仅记录参与邀请的兑换事实。兑换码首次成功兑换时，在同一事务中记录归属、额度和时间，奖励金额仍取自原有 `referral_rewards`，不会重复发奖或改变兑换金额。这使邀请人注销后产生的未发放记录，在受邀人也注销后仍可查询。迁移只回填已有事实或仍可追溯的兑换，不猜测已经丢失的历史归属。

## 部署与回滚

先核对目标环境和已应用迁移，再应用 `20261117131223_referral_rewards.sql`；管理员统计及兑换审计使用后续的 `20261117134750_admin_referral_overview.sql`。数据库准备完成后再发布对应后端及前端。不要因本地与远端迁移时间戳不同而重跑已有 SQL，也不要把隔离测试用的用户、兑换码或奖励写入正式库。

网站版本回滚时保留新表、奖励流水与绑定记录；前端旧版本不显示入口，但数据库兑换仍会自动履行已绑定的奖励。若需要停用奖励，须单独审核后端数据库策略，不能通过删除流水或奖励表回滚余额。

数据库回归测试覆盖全额到账、10% 奖励、重复兑换、旧兑换不补发、禁止换绑、账号隔离与权限边界。另有后端接口测试与前端邀请码/请求测试。真实邮件投递和用户设备网络仍由现有认证服务负责。
